# 墨韵阁 · 优化分析报告（2026-08-09）

**日期**: 2026-08-09
**范围**: 基于当前代码现状（1.4 万行，Next.js 15 + Upstash Redis + IndexedDB）的全面优化机会分析
**性质**: 分析文档，不包含代码改动

---

## 一、现状能力盘点

| 维度 | 已有能力 |
|------|----------|
| 组织架构 | 6 预置藏 + 自建藏；每藏独立印章/色调/布局（classic/list/gallery） |
| 节气系统 | 24 节气元数据、季节色、动态背景（雪/雨/叶/萤/瓣）、节气动效 |
| 搜索 | Fuse.js 模糊 + 拼音（全拼/首字母）+ AI 语义搜索 + 6藏×4季筛选 + ⌘K + 历史 + URL 同步 |
| AI | 赏析 / 两步配图（提示词→生图）/ 打标签 / 语义搜索 / 批量标签；自定义 API Key；30 天缓存；限流 |
| 数据 | Redis 持久化 + IndexedDB 离线降级 + 每日备份 + 30 天快照历史 + 手动导入导出 + 异地推送（可选） |
| 展示 | 卷轴/毛笔逐字/印章/水墨/暗色/字号/分享卡片（Canvas 壁纸）/ 接龙 / 统计热力图词云 |
| 工程 | PWA 离线 + 回收站 30 天 + 错误边界 + 服务端密码鉴权 + 软删除 |

**成熟度判断**: 功能完整度高，处于"能用、好看、有特色"阶段；下一步优化应聚焦 **① 数据资产的长期安全与规模承载 ② 使用深度的体验增强 ③ 性能与工程质量**。

## 二、优化建议（按优先级 P0/P1/P2）

### P0 数据资产与安全（先做）

| # | 建议 | 现状问题 | 方案 |
|---|------|----------|------|
| 1 | **AI 配图持久化到对象存储** | `coverImage` 存第三方临时 URL（有 dataURL 兜底但 4MB 上限会退回原 URL，且 dataURL 撑 Redis） | 接入对象存储（R2/S3/自建）或直接存 dataURL（需评估 Redis 容量）；设图片压缩（WebP/降分辨率） |
| 2 | **生产部署凭据就绪** | 本地已配置；Vercel 生产需 POEM_PASSWORD/CRON_SECRET/NEXT_PUBLIC_SITE_URL；GitHub 推送 403 未解决 | 补 Vercel 环境变量 + 解决推送权限（见遗留事项） |
| 3 | **TTS 预生成落地** | 路由支持静态音频，但 `public/audio/` 为空，生产仍浏览器降级 | 本地执行 `node scripts/tts-pregen.mjs` 生成 mp3 提交部署 |
| 4 | **收藏语义澄清** | `favoriteCount` 实为 0/1 冗余（注释已说明），多用户场景会误导 | 若维持单用户可简化；若规划多用户需重构收藏表 |

### P1 功能增强（用户价值高）

| # | 建议 | 说明 |
|---|------|------|
| 5 | **经典诗词导入** | 目前只能手写/手动导入 JSON。可内置《唐诗三百首》等公版诗集一键导入（或 URL/剪贴板导入） |
| 6 | **诗词日历视图** | 现有"节气/季节"维度，可加"日期视图"（按创作日期月历展示，呼应"藏时光"定位） |

| 8 | **分享链接公开页** | 现有 Canvas 分享卡片是图片；可加 `/share/[id]` 公开只读页（无鉴权、无写入），便于发朋友圈/群里 |
| 9 | **数据统计增强** | 现有热力图/词云/季节分布；可加"收藏 Top10""最长连续写作天数""节气写作分布" |

### P1 性能与体验

| # | 建议 | 现状问题 | 方案 |
|---|------|----------|------|
| 11 | **图片懒加载 + next/image** | coverImage 直接 `<img src>`，无懒加载/尺寸优化 | 用 `next/image`（或 loading="lazy" + width/height），瀑布流/画廊场景收益明显 |
| 12 | **字体体积** | 根布局加载 Google Fonts（Ma Shan Zheng + Noto Serif SC 多字重），首屏字体阻塞 | 字体子集化 + `display=swap`（已用）+ 仅加载用到的字重；或本地化字体文件 |
| 13 | **API 响应缓存** | `/api/poems` 每次全量拉取 | SSR 页面对诗词列表加 `fetch` 缓存（Next 15 `cache: 'force-cache'` 或 Redis 层缓存 + 失效策略） |
| 14 | **路由级分包** | First Load JS 已优化到 196KB（搜索 Modal 已动态导入） | 可继续：stats/chain/tags 等低频页面的图表/接龙引擎按需加载 |
| 15 | **骨架屏与空状态** | 部分页面 loading 态简单 | 为列表/详情/搜索补骨架屏；空藏/空结果给出引导（去写第一首诗） |
| 16 | **无障碍** | 未系统做 a11y | 焦点管理（⌘K 弹窗）、aria-label、键盘导航、对比度检查 |

## 三、不建议做（避免过度工程）

- **LazyMotion 深层分包**：已核查 v11.18.2 无法真分包（`framer-motion/m` 子路径不导出 `m`/`AnimatePresence`，`layoutId` 依赖 `domMax`），收益与复杂度不成比例。
- **自研搜索服务**：Fuse.js 在数千首规模内足够，无需 Elasticsearch。
- **数据库迁移**：Redis + IndexedDB 双写已满足单用户规模，引入 Postgres 收益小。

---

## 四、建议执行顺序

1. **P0-1/2/3**（数据安全与部署就绪）——一周内
2. **P1-5/6/8**（导入/日历/分享页）——按产品优先级选 1-2 个
3. **P1-11/12/13**（性能）——随功能迭代穿插
4. P2 方向需用户决策后再评估
