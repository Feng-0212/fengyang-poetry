# 墨韵阁 —— 随节气流转的 AI 诗词书院

**项目说明文档**（AI 创意编程赛 · 高中组）

---

## 一、创意来源与需求分析

**为谁解决什么问题？** 中国是诗的国度，但传统诗词收藏工具大多是"数据库式"的：打开一个列表，输入标题，保存——缺乏文化氛围，也缺少智能化的整理与创作辅助。我们观察到身边同学学古诗、写现代诗时遇到三个真实痛点：

1. **收藏无趣**：想收藏诗词却找不到有"仪式感"的地方，节气、四季的意境无从体现；
2. **创作孤单**：想写诗没人交流，也缺少灵感辅助；
3. **整理困难**：诗词越存越多，标签、分类、回顾、统计全靠手工。

于是我们决定开发 **墨韵阁**：一座"随节气流转的诗意书院"。它以中国 24 节气为骨架组织诗词收藏，用 AI 提供赏析、配图、续写、仿写等创作辅助，并开放注册形成社区（收藏、评论、关注、同题创作），让"藏诗"变成一件既有文化韵味、又有智能助力的事。

**需求拆解**：从"发现痛点"→"需求拆解"（收藏管理、节气组织、AI 辅助、社区互动、数据安全五大模块）→"系统设计"（多藏架构、账号权限、可见性规则）→"技术实现"→"测试验证"，我们走完了从需求分析到系统设计的完整开发流程，也正因如此，作品的功能边界清晰、没有过度设计。

**为什么不能直接用现成工具**：市面上虽有诗词类 App，但大多只解决"收藏"或"创作"的单一环节——要么是冷冰冰的数据库式列表，要么是单纯的创作论坛。我们想要的是把节气文化、AI 智能与社区温度融为一体的一处"书院"，这正是墨韵阁的差异化定位所在。

**典型使用场景**：

- **场景一 · 藏诗**：霜降之夜，同学读到《枫桥夜泊》，想把它"珍藏"起来——打开墨韵阁，按节气自动归入"四时墨苑"，一键生成 AI 赏析与 AI 配图，一首诗就有了自己的"居所"；
- **场景二 · 创作**：写诗写到一半思路枯竭，点"AI 续写"让它保持句式韵脚接续；想学"王维山水田园"的风格，点"AI 仿写"一键生成新诗，再人工润色；
- **场景三 · 社区**：登录后收藏他人作品、留下评论、关注喜欢的墨客，参加"节气同题创作"；作品默认公开、可一键切换私密，既有展示的机会，也有隐私的保障。

## 二、作品功能设计（核心功能 ≥ 5）

**设计原则**：功能设计遵循"文化为骨、AI 为翼、安全为本"——先保证收藏与创作的基本体验完整可用，再叠加 AI 能力降低使用门槛，最后用权限体系与数据备份守住底线。

| # | 功能 | 说明 |
|---|------|------|
| 1 | **多藏诗词管理** | 6 个预置藏（四时墨苑/月下山河/关山词/烟雨阁/童心斋/新诗林）+ 自建藏；每藏独立印章、色调、布局；增删改查、软删除回收站（30 天自动清理） |
| 2 | **24 节气系统** | 全年 365 天节气区间表（程序化校验无空洞、无重叠）；节气自动识别、季节色、动态背景（雪/雨/叶/瓣）；按节气/季节组织诗库，月历视图浏览"哪天写了什么" |
| 3 | **AI 能力套件** | AI 赏析（30 天缓存节省 token）、AI 配图（两步生图 + sharp 压缩 WebP 自包含存储）、AI 打标签（统一 24 标签池 + 批量）、**AI 续写**、**AI 仿写**、AI 语义搜索 |
| 4 | **多用户社区** | 邮箱注册登录（scrypt 哈希 + Bearer 会话）；公开/私密可见性（私密仅本人可见）；真实收藏计数（去重）、评论、关注、节气同题创作、用户主页 |
| 5 | **智能搜索** | Fuse.js 全文模糊 + 拼音（全拼/首字母，输入防抖）+ AI 语义搜索 + ⌘K 快捷键 + 多藏×多季筛选 + 实时高亮 + URL 同步 |
| 6 | **展示与体验** | 卷轴/毛笔逐字动画、Canvas 分享壁纸（三尺寸三风格）、分享公开页（微信直开）、真人级 TTS 朗读（5 音色，列表连续朗读）、暗色模式、PWA 离线 |
| 7 | **数据与安全** | 每日自动备份 + 30 天快照回溯 + 可选异地推送；AI 接口 Redis 滑动窗口限流；写操作需登录 + 归属校验（仅本人可改自己的诗）；经典诗词一键导入（12 首公版唐诗宋词，按标题查重） |

**功能亮点**：一是"节气即骨架"——首页氛围、诗库组织、日历视图都由 24 节气驱动，让传统文化可感知；二是"AI 即书童"——赏析、配图、标签、续写、仿写、语义搜索六项 AI 能力覆盖"收藏—整理—创作"全链路，且结果可缓存、可限流、成本可控；三是"安全即底线"——数据每日备份、私密内容服务端强制隔离，让社区开放与数据安全兼得。

## 三、技术选型说明

| 类别 | 选型 | 理由 |
|------|------|------|
| 框架 | Next.js 15（App Router） | 服务端组件 + 客户端组件混合渲染，SEO 好、首屏快 |
| 数据 | Upstash Redis + IndexedDB | Redis 云托管（免运维、支持限流计数）；IndexedDB 本地缓存离线降级 |
| 样式 | Tailwind CSS 3 | 原子化样式，配合 CSS 变量实现"水墨 + 暗色"主题 |
| 动效 | Framer Motion | 卷轴展开、墨迹晕染等文化感动效 |
| 搜索 | Fuse.js | 轻量模糊匹配，几千首规模足够，避免引入重型搜索服务 |
| 鉴权 | 自建 scrypt + Bearer Token | 无第三方依赖，密码加盐哈希存储 |
| 图像 | sharp | AI 生成图压缩为 WebP 自包含，避免图床链接过期 |
| 朗读 | Edge TTS 预生成 | 真人级中文神经网络音色，静态分发 + 缓存 + 浏览器降级 |

**模块化设计**：数据访问统一收敛在 `lib/store.ts`（消除 9 个 API 路由约 300 行重复代码），AI 能力封装在 `lib/ai.ts`，用户/权限在 `lib/user.ts`，类型统一收敛在 `src/types/poem.ts`。页面按路由分包，低频模块动态导入（SearchModal 单独分包使首屏体积 235KB→196KB）。整体呈"页面层 → 组件层 → API 层 → 服务层"单向依赖，结构清晰、易于维护。

## 四、AI 辅助编程工具使用记录

本项目是**两阶段人机协同开发**：基础版本由 **Qclaw**（AI 辅助编程工具）完成主体功能开发；随后我们使用 **DeepCode**（AI 编程智能体）在完整审阅代码的基础上，进行系统性缺陷修复与功能增强。两个阶段 AI 生成的代码均经过人工逐行审查、联调与回归验证后才合入主线。

**为什么选这两款工具**：Qclaw 擅长从零快速搭建完整可运行的应用，把想法高效变成产品；DeepCode 擅长在已有代码库上做"体检"——定位缺陷、给出修复方案、按计划批量落地。两者互补，正好覆盖"从 0 到 1"和"从 1 到 N"两个阶段。

| 环节 | AI 生成了什么 | 人工修改/决策 |

| 需求与架构 | 多藏架构（6 预置藏 + 自建藏）、24 节气系统、数据模型（Poem/Collection） | 人工确定产品定位与核心功能范围，避免功能发散 |

| 遗留风险修复 | 写操作安全加固（未配置即拒绝）、AI 配图自包含存储、TTS 静态音频、异地备份、首屏体积优化（235→196KB） | 人工确认部署策略与数据方案 |

| 模块化重构 | 抽取统一数据访问层 `lib/store.ts`，消除 9 个 API 路由约 300 行重复代码 | 人工验证构建与全链路回归 |

**典型人机协同案例**（DeepCode 阶段）：

1. **AI 生成代码 + 人工定位根因修复 bug**：AI 生成的 AI 配图功能，实测发现"图片下载需 20 秒、原 15 秒超时必然失败，且 1.4MB 原图转 dataURL 会超 Upstash 单 key 1MB 限制"。人工定位根因后，指导 AI 改为"下载后一律 sharp 压缩为 WebP 再存储"，实测 1.4MB → 207KB，裂图问题根治。
2. **AI 排查 + 人工验证**：部署时遇到 `Cannot find module './vendor-chunks/...'`，AI 定位是 dev server 与 build 并发污染 `.next` 目录，人工确认规避策略（重建后立即测试、换端口）。
3. **AI 建议 + 人工决策**：AI 分析"LazyMotion 无法真分包"（框架版本限制），建议不做深层分包，人工采纳避免过度工程。

**工具使用小结**：Qclaw 用于基础版本快速成型；DeepCode 用于代码审查、缺陷定位、功能增强与重构。整个流程遵循"AI 生成 → 人工审查 → 联调验证 → 合入主线"，人工始终负责需求决策、代码审查、测试验证与部署——AI 是"协作者"而非"替代者"，这正是本作品在 AI 辅助编程方面的真实实践。

## 五、开发中的关键问题与解决记录

| 问题 | 根因 | 解决方案 |
|------|------|----------|
| 节气表数据错误（10 月误显示"立春"） | 数据表存在垃圾占位记录 | 重写全年 365 天区间表，Node 脚本程序化验证无空洞、无重叠 |
| 写作热力图永远为空 | createdAt 类型为 number + UTC 日期偏移 | 改用 Date 本地时区生成日期键，并兼容旧数据 |
| AI 配图裂图 | 第三方图片 URL 过期 + 下载超时过紧 | 下载后 sharp 压缩为 WebP 自包含存储（1.4MB→207KB） |
| 备份历史接口无 Redis 时 500 | 两路由获取 KV 的行为不一致 | 统一走 `lib/kv.getKv()`（含内存回退），行为对齐 |
| 标签池三处不一致（18/24/12） | 各模块硬编码标签列表 | 新建 `lib/tags.ts` 统一 24 标签池，三处同源引用 |
| 写操作无保护 | 旧版密码机制有静默放行风险 | 重构为账号体系：scrypt 哈希 + 会话，生产未配置即拒绝（503） |
| 私密诗泄露 | 读接口未过滤可见性 | 服务端统一可见性过滤：私密仅本人可见，他人/未登录返回 404 |
| 首屏体积大 | 搜索依赖全量打包 | SearchModal 动态导入（fuse.js 分包），235KB→196KB |
| 请求冗余 | 一页多处 hook 重复拉取 | 客户端短 TTL 缓存 + 并发请求去重（5 次请求合并为 1 次） |
| 本地推送失败 | GitHub 直连被网络重置 | 走本地代理推送（git -c http.proxy=...） |

**测试策略**：每个功能模块完成均执行 `next build`（类型检查 + 全路由生成）+ 生产模式（`next start`）端到端实测；注册→登录→建诗→收藏→评论→关注全链路验证；缺陷修复采用"计划书→分批修复→交付记录→回归验证"流程，15 项缺陷全部闭环，测试数据清理后上线。

**片段一：AI 续写 API（`src/app/api/ai/write/route.ts` 节选）**——调用文本模型续写/仿写，含限流与空返回重试：

```ts
export async function POST(req: Request) {
  // AI 接口限流：每 IP 每 60 秒最多 8 次
  const rl = await writeLimiter.check(req);
  if (!rl.success) return new Response(null, { status: 429, headers: {...} });

  const { key, baseUrl, model } = resolveConfig(req); // 个人 Key > 站点 Key
  const mode = body.mode === "parody" ? "parody" : "continue";
  // continue：给已有诗句续写；parody：按主题/风格创作新诗
  const system = mode === "continue"
    ? "你是一位深谙古典诗词格律的诗人。请根据用户给出的已写诗句，自然地续写完整……"
    : "你是一位古典诗词大家。请根据用户指定的主题或参考风格，创作一首完整的新诗……";

  let resp = await callModel();
  let text = extractText(await resp.json());
  if (!text) {           // 空返回自动重试一次
    resp = await callModel();
    text = extractText(await resp.json());
  }
  return NextResponse.json({ text });
}
```

**片段二：收藏切换 API（`src/app/api/poem/[id]/favorite/route.ts` 节选）**——登录鉴权 + 去重计数 + 可见性校验：

```ts
export async function POST(req: NextRequest, { params }) {
  const auth = await requireUser(req);      // 未登录 → 401
  if ("error" in auth) return auth.error;
  const user = auth.user;

  const poem = poems[idx];
  // 私密诗仅作者可操作（他人 404）
  if (!isPoemVisible(poem, user.id)) return NextResponse.json({ error: "Not found" }, { status: 404 });

  const favs = poem.favoritedBy || [];
  const already = favs.includes(user.id);
  poem.favoritedBy = already ? favs.filter(id => id !== user.id) : [...favs, user.id];
  poem.favoriteCount = poem.favoritedBy.length;   // 真实收藏计数
  await setPoems(poems);
  return NextResponse.json({ favorited: !already, favoriteCount: poem.favoriteCount });
}
```

  // SOLAR_TERM_BY_DATE: 365 条 { start, end, key } 区间表（已程序校验无空洞/重叠）
  const day = startOfYearDay(date);
  const found = SOLAR_TERM_BY_DATE.find(r => day >= r.start && day <= r.end);
  return SOLAR_TERMS_META.find(t => t.key === (found?.key || "lichun"))!;
}
